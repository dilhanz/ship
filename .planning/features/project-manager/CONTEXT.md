## Problem

Ship manages individual features well, but nothing sits above them: no milestone tracking, no cross-feature prioritization, no dependency awareness, and no persistent answer to "what should I work on next, and what can run in parallel?" Project-level knowledge — decisions, priorities, blockers, direction — has no home and gets lost between sessions.

## Solution

Add a lightweight Project Manager layer to the Ship plugin that maintains its own state under `.project-manager/` at the repo root. Two new skills: `/ship:pm` is a question router that answers freeform PM questions (next recommendation, parallel work, status, decision history) and gives a high-level brief when invoked without arguments; `/ship:pm-sync` is an interactive session that bootstraps the folder on first run (scan repo → propose → interview → confirm) and thereafter reconciles PM state with reality and captures anything missing. A hook nudges Claude to sync PM state when Ship feature statuses change, without modifying existing skills. Every PM command regenerates a self-contained static `dashboard.html` when state changed. The PM directs and recommends but never implements — recommendations end with the concrete Ship command to run.

## Decisions

- **Packaging — part of the Ship plugin:** new skills live in this repo, namespaced `/ship:pm` and `/ship:pm-sync`; the PM natively understands `.planning/features/` as the feature-level source of truth and sits above it as the milestone layer.
- **Command surface — question router + sync:** `/ship:pm` answers the question asked (freeform args) rather than dumping a fixed report; no args → high-level brief. `/ship:pm-sync` is the only interactive capture/update session.
- **Bootstrap — guided interview via `/ship:pm-sync`:** first run detects missing `.project-manager/`, scans README, git log, and `.planning/features/`, proposes draft milestones/backlog, and interviews the user before writing state. The same command is reused to update PM state with anything missing later.
- **Ship lifecycle sync — hook-driven nudge:** a hook detects feature status changes and injects a reminder for Claude to sync PM state; existing Ship skills are not modified. Rationale: loosest coupling, no behavioral risk to the build/finish flow.
- **State shape — few markdown files:** `ROADMAP.md` (milestones, features, status, priorities, dependencies), `DECISIONS.md` (dated decision log with rationale), `dashboard.html` (generated). Human-readable, git-diffable, no duplication of what `.planning/features/` already records.
- **Dashboard — static self-contained HTML:** regenerated by any PM command whenever state changed; opened via `file://`; zero server, zero dependencies, no external requests; strictly read-only and high-level (milestones, progress, priorities, blockers, next up).
- **No time concepts:** no dates, estimates, or sizing anywhere in PM state — only priority order, status, and dependencies. Rationale: maximum lightweight, avoids stale-date rot.
- **No-implementation rule — soft guidance:** skill instructions forbid implementation work and require recommendations to hand off to Ship commands (e.g. `/ship:start "X"`); no tool-level enforcement.
- **Git-neutral:** the skill never imposes committing vs. gitignoring `.project-manager/`; that stays the repo owner's choice.
- **NFR — error handling:** PM commands must degrade gracefully when state files are missing or malformed (offer to run/repair via `/ship:pm-sync` rather than erroring out).
- **NFR — performance/observability/rollout:** not applicable — markdown-reading skill with a static HTML output; no runtime of its own.

## Acceptance Criteria

- [ ] Running `/ship:pm-sync` in a repo with no `.project-manager/` runs a guided interview (repo scan → proposed milestones/backlog → user confirmation) and creates `ROADMAP.md`, `DECISIONS.md`, and `dashboard.html`.
- [ ] `/ship:pm what should I work on next?` answers with a specific recommended item, the rationale grounded in recorded priorities and dependencies, and the concrete Ship command to start it; `/ship:pm` with no arguments produces a high-level brief (milestones, progress, blockers, next up).
- [ ] `/ship:pm` can identify which backlog items are safe to work on in parallel, based on the dependencies recorded in `ROADMAP.md`.
- [ ] `dashboard.html` is a single self-contained file that renders milestones, overall progress, priorities, blockers, and next-up in a browser via `file://` with no server and no external network requests, and is regenerated by any PM command that changed state.
- [ ] When a Ship feature's status changes, a hook injects a nudge to sync PM state; after `/ship:pm-sync`, `ROADMAP.md` reflects the feature's new status.
- [ ] The PM never writes outside `.project-manager/` and never begins implementation work — its recommendations end with a Ship command handoff.
- [ ] PM state files contain no dates-as-deadlines, estimates, or sizing fields (decision-log timestamps are allowed).

## Scope

**In scope:**
- Two new skills: `skills/pm/SKILL.md` (`/ship:pm`) and `skills/pm-sync/SKILL.md` (`/ship:pm-sync`)
- `.project-manager/` state: `ROADMAP.md`, `DECISIONS.md`, generated `dashboard.html`
- Hook-driven nudge for PM state sync on Ship feature status changes (new hook, registered in `hooks/hooks.json`; existing skills untouched)
- Dashboard generation as part of PM command runs

**Out of scope:**
- Task-level tracking or a detailed task-management interface
- Time concepts: target dates, estimates, sizing, velocity
- Any server, npm dependency, or external network access for the dashboard
- Tool-level enforcement of the no-implementation rule (soft guidance only)
- Modifying existing Ship skills (`start`, `build`, `finish`, `go`, …)
- Imposing a commit-vs-gitignore policy for `.project-manager/`

## Codebase Notes

- Skills are auto-discovered from `skills/*/SKILL.md` and auto-namespaced `ship:{dir-name}` — a `skills/pm/` directory yields `/ship:pm`. Descriptions should use the "Use when… / TRIGGER when…" format used by the other 14 skills.
- Hooks are zero-dependency stdin→stdout Node scripts in `hooks/`, registered declaratively in `hooks/hooks.json` with `${CLAUDE_PLUGIN_ROOT}` paths; they must never throw or block. `hooks/scan-features.cjs` already scans `.planning/features/` frontmatter for statuses — the PM sync nudge can reuse the same scanning approach and compare against statuses recorded in `ROADMAP.md`.
- `hooks/guide.cjs` (SessionStart) and `hooks/post-compact.cjs` show the `hookSpecificOutput.additionalContext` injection pattern the nudge hook should follow.
- Feature status lives in each feature's `CONTEXT.md` frontmatter (`brainstormed` → … → `done`); completed features move to `.planning/archive/{name}/`. Both locations matter for reconciliation.
- Templates read at runtime live in `ship/templates/` — a dashboard HTML template could live there alongside `VERIFY.md`'s template.
- Tests use `node --test` with files in `tests/` (on Windows/Node 22 use the glob form `node --test "tests/*.test.js"`).
